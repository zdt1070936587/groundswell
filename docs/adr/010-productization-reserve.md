# ADR-010 产品化预留：鉴权、多租户、计费

## 背景

观潮先作为内部工具使用（单用户 / 小团队），但希望保留产品化的空间：对外提供订阅、Newsletter、团队版。现在就做账号体系和多租户会显著拖慢核心能力（采集、话题、商机）的迭代；完全不预留，将来改造会波及所有表和查询。

## 决策

现在只做“低成本、改变接口形状”的预留，不做具体实现：

1. **鉴权分层**
   - API：单 token（`GS_API_TOKEN`，Bearer）中间件，所有 `/api/*` 统一入口；`/healthz` 永远开放。
   - Web：浏览器只访问 Next.js 同源 `/api/*`，由服务端代理附加 token，token 不下发到浏览器；整站可选 Basic Auth（`GS_WEB_USER` / `GS_WEB_PASSWORD`）。
   - 将来换成 OAuth / 账号体系时，只替换这两个中间件，业务接口不变。
2. **查询集中**：所有读查询经过 `queries.py`，写操作经过 `ideas.py` / `subscriptions.py` / `funnel.py` 等领域模块，API 与看板不直接写 SQL。多租户时在这些函数上加 `workspace_id` 参数即可，改动面可控。
3. **数据分层**：采集层（`raw_items`、`topics`、统计表）是全局共享的公共数据，不加租户字段；只有“用户产生的数据”——反馈、点子库、评论、订阅——将来需要 `workspace_id`。这些表目前都有 `user_name` / `owner` 字段记录操作者，协作（评论、分派、看板）已按单工作区实现。
4. **出口统一**：推送走 `reporting/dingtalk.py`，报告以 Markdown 文件落盘并通过 `/api/reports` 暴露。Newsletter / 邮件 / Slack 出口将来作为新的推送器实现同一个“标题 + Markdown”接口。
5. **计费预留**：LLM 成本已按阶段记账（`llm_usage.stage`），将来按租户计费只需在记账时带上 `workspace_id`。

## 触发条件

出现以下任一情况时启动产品化改造：外部付费意向 ≥ 3 家；或内部使用者 > 10 人且需要数据隔离。

改造顺序：账号与工作区表 → 用户数据表加 `workspace_id`（迁移时默认值为内部工作区）→ 订阅 / Newsletter 出口 → 计费。采集层、话题层、商机分析不改。

## 后果

- 当前代码没有租户概念，内部使用零负担。
- 产品化时的改造集中在鉴权中间件、`queries.py` 和四张用户数据表，核心流水线不动。
- 代价：在此之前，所有用户共享同一个点子库与订阅列表。
